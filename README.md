# totp-auth

A self-hosted web authenticator for one person. It stores your TOTP secrets end-to-end
encrypted behind an account (username and password, with a downloadable recovery key), shows live codes synced to the
server clock, and exports and imports plain `otpauth://` URIs.

## Requirements

- Node.js 24 (see `.nvmrc`) and npm
- Docker with Compose (for Postgres 17, and optionally the app container)

## Quick start (development)

```bash
cp .env.example .env
# Fill in the secret:
openssl rand -base64 32   # paste as SERVER_PEPPER

npm ci
npm run db:up             # Postgres on 127.0.0.1:5433
npm run dev               # http://localhost:3000
```

Migrations run automatically when the server starts (`src/instrumentation.ts`, under a
Postgres advisory lock so several instances never migrate at once). To apply them by hand:
`npm run db:migrate`. After changing `src/db/schema.ts`, run `npm run db:generate` and
commit the new files in `drizzle/`.

Open the app and create the account. Registration closes as soon as one account is confirmed.

## First run: creating the account (setup token)

A fresh instance has no account, and whoever registers first owns it. To stop a stranger from
claiming a new public instance before you do:

- On a **loopback** origin (`APP_ORIGIN` is `http://localhost…`, `http://127.0.0.1…` or
  `http://[::1]…`) you can register without a token. This is the development case.
- On **any other origin**, registration stays **closed** until you set `SETUP_TOKEN`. The sign-up
  page then asks for it. `GET /api/auth/config` reports
  `{"registrationOpen": false, "closedReason": "setup_token_missing"}` until then.

```bash
openssl rand -base64 24          # put this in .env as SETUP_TOKEN (at least 16 characters)
docker compose --profile app up -d
# open https://your-domain/register, enter the token, create your account and download your recovery key
```

After your account is created, registration closes for good (unless `ALLOW_REGISTRATION=true`).
You can then remove `SETUP_TOKEN` from `.env`. The token is never generated by the server or
printed to logs: it lives only in your environment, so every instance behaves the same.

A sign-up that is not finished within an hour is deleted. Until then, only the browser that
started it can restart it for the same username.

## Running with Docker Compose

```bash
cp .env.example .env      # fill in secrets, set APP_ORIGIN to the public URL
docker compose --profile app up -d --build
```

The app listens on `127.0.0.1:3000`. Put a TLS-terminating reverse proxy in front of it (see
below). The image runs as a non-root user, uses Next's standalone output and has a
`HEALTHCHECK` against `GET /api/health`. Compose runs it with a read-only root filesystem, a
tmpfs at `/tmp`, all Linux capabilities dropped and `no-new-privileges`.

Base images are pinned to a minor version (`node:24.11-alpine3.22`). For fully reproducible
builds you can also pin the digest:
`docker buildx imagetools inspect node:24.11-alpine3.22` shows it; then use
`FROM node:24.11-alpine3.22@sha256:<digest>`. The same works for `postgres:17-alpine` in
`docker-compose.yml`.

## Deploying to Vercel

Development uses the Docker Postgres from `docker-compose.yml` (`.env`). Production on Vercel uses
a managed Postgres (Neon) through environment variables set in the Vercel project; nothing from
`.env` is deployed.

1. Put the production values in Vercel (Production scope only, so preview builds never migrate the
   production database). `.env.production.local` (gitignored) holds a ready set:

   ```bash
   vercel link --project totp-auth
   grep -v '^#' .env.production.local | while IFS='=' read -r k v; do
     printf '%s' "$v" | vercel env add "$k" production
   done
   ```

   `APP_ORIGIN` is preset to `https://totp-auth.vercel.app` (project name `totp-auth`); change it if Vercel assigns a different domain or you add a custom one.
2. `vercel --prod` (or push to the connected Git branch). The `vercel-build` script runs
   `drizzle-kit migrate` against `DATABASE_URL` and then `next build`.
3. Open `/register`, enter `SETUP_TOKEN`, create the account, download the recovery key.

Notes: on Vercel the server does not migrate at startup (the build does), `TRUST_PROXY=true` is
correct because Vercel overwrites `X-Forwarded-For`, and the pg pool is small and attached to the
Fluid-compute lifecycle. Use `sslmode=verify-full` in the Neon URL.

## Environment variables

| Name | Required | Meaning |
| --- | --- | --- |
| `DATABASE_URL` | yes | `postgres://` connection string. |
| `SERVER_PEPPER` | yes | 32 random bytes, base64. HMAC key for recovery keys and decoy salts. |
| `APP_ORIGIN` | yes | Public origin, e.g. `https://auth.example.com`. Used for the Origin check and cookie flags. Must match what the browser shows exactly. |
| `ALLOW_REGISTRATION` | no | `true` keeps registration open after the first account. Default `false`. |
| `TRUST_PROXY` | no | `true` to read the client IP from `X-Forwarded-For` for rate limits. Default `false` (`true` in `docker-compose.yml`, which only binds 127.0.0.1 behind a proxy). |
| `SETUP_TOKEN` | first run on a public origin | At least 16 characters (`openssl rand -base64 24`). Required to open registration on a non-loopback origin; when set, registration always asks for it. |
| `DATABASE_URL_TEST` | tests | Separate database for `npm test`. Never point it at real data. |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | compose | Used by the `db` service. |

The server validates all of these at startup and exits with a message naming the bad keys.
It never prints their values. With `NODE_ENV=production` (the Docker image) it also refuses to
start while `DATABASE_URL` or `POSTGRES_PASSWORD` still use the example password `change-me`.

Do not lose or rotate `SERVER_PEPPER` casually: a new pepper invalidates every recovery key
and changes the decoy salts shown for unknown usernames.

## Security model (summary)

Full details: `docs/ARCHITECTURE.md`.

- **The server cannot read your vault.** The browser derives two keys from your password
  with Argon2id: an `authKey` sent to the server, and a vault key that never leaves the
  browser. Entries are encrypted with AES-256-GCM in the browser; the server stores only
  ciphertext.
- **Login is username and password.** The server stores `argon2id(authKey)`. There is no
  second factor: anyone with your password can sign in, so use a long, unique one.
- **The recovery key** (one per account, 20 characters, downloaded at registration) lets you
  set a new password if you forget the old one. It restores **account access only**: the
  vault is encrypted with a key derived from your old password, so recovering **erases every
  saved entry**. Keep a plain export (Account menu, Export) offline. The server stores only
  an HMAC of the key. Using it replaces it with a new one.
- **Sessions** are random 32-byte tokens in an `HttpOnly`, `SameSite=Strict` cookie
  (`__Host-sid` over HTTPS). The database stores only their SHA-256. Signed-in sessions last
  at most 14 days and end after 3 idle days. Changing the password signs out other sessions.
- **CSRF**: every state-changing API call must come from `APP_ORIGIN` with
  `Content-Type: application/json`.
- **Rate limits** are stored in Postgres. Sign-in, recovery and unlock count **failed** attempts
  only: 5 per username and IP in 15 minutes, 30 per username per hour from all IPs together,
  30 per IP in 15 minutes. A successful sign-in clears that username and IP bucket. So a stranger
  guessing from elsewhere cannot lock you out with a handful of attempts, and spread-out guessing
  is still capped. The cost of that cap: about 30 failures an hour from many addresses can block
  sign-in for that username until the hour ends. Prelogin and register have plain per-IP caps.
- **Known trade-off with `TRUST_PROXY=false`:** every client shares one "unknown" IP bucket, so
  failures from anyone count against everyone's IP limit. Behind a reverse proxy, set
  `TRUST_PROXY=true`.
- **Request bodies** are capped per route: 8 KiB for auth routes, 16 KiB to create or update an
  entry, 1 MiB for import, 4 MiB for a password change. The body is read as a stream and cut off
  past the cap with 413.
- **Headers**: strict nonce-based CSP, HSTS (HTTPS only), `nosniff`, `no-referrer`, COOP,
  and `Cache-Control: no-store` on every API response.
- Unknown usernames get the same responses and the same Argon2 work as wrong passwords.

## Reverse proxy notes

- Serve the app over HTTPS and set `APP_ORIGIN` to the exact public origin (scheme, host,
  port if non-standard). Requests with any other `Origin` are rejected with 403.
- Forward the original `Host` and do not rewrite the `Origin` header.
- `TRUST_PROXY=true` (the Compose default) is safe **only** if your proxy **overwrites**
  `X-Forwarded-For` with the real client address instead of appending to what the client sent.
  The server uses the right-most address in that header. If the app port is reachable without
  going through the proxy, clients can forge their IP and dodge per-IP limits.
- Do not expose port 3000 directly to the internet; Compose binds it to `127.0.0.1`.
- Cap request bodies at the proxy too (the app also enforces its own caps): 4 MiB is enough
  for every route.
- Health checks: `GET /api/health` returns `200 {"ok":true}` when the instance can reach
  Postgres, otherwise `503`. During shutdown it returns 503 so the load balancer stops routing
  to the instance.

Caddy (sets `X-Forwarded-For` from the real peer address, replacing any client value):

```
auth.example.com {
  request_body {
    max_size 4MB
  }
  reverse_proxy 127.0.0.1:3000
}
```

nginx:

```
server {
  server_name auth.example.com;
  client_max_body_size 4m;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;   # overwrite, never $proxy_add_x_forwarded_for
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
```

## Stateless operation and scaling

The app process keeps no user state. You can run any number of identical instances behind a load
balancer, without sticky sessions, and throw containers away at will.

| What | Where |
| --- | --- |
| Accounts, encrypted vault entries, recovery-key hashes | Postgres |
| Sessions (only the SHA-256 of each token) | Postgres `sessions` |
| Rate-limit counters | Postgres `rate_limits` |
| Migration state | Postgres (`drizzle.__drizzle_migrations`) |
| Server secrets and configuration | Environment variables |
| Files on disk | None. The container runs with a read-only root; only `/tmp` (Next's cache) is writable |

- Every instance must get the **same** `SERVER_PEPPER`, `APP_ORIGIN`,
  `DATABASE_URL`, `ALLOW_REGISTRATION`, `TRUST_PROXY` and `SETUP_TOKEN`. Different keys or a different
  pepper on one instance would break recovery keys there.
- Startup migrations take a Postgres advisory lock. A second instance waits, then finds nothing
  to apply.
- Cleanup of expired sessions and rate-limit rows runs opportunistically in small batches. It is
  safe when several instances do it at once.
- On `SIGTERM` an instance stops accepting connections, finishes in-flight requests, reports 503
  on `/api/health` and closes its database pool.
- Back up Postgres (and keep a copy of your `.env` secrets). There is nothing else to back up.

## Backups

Everything lives in Postgres. Back up the database and your `.env` (at least
`SERVER_PEPPER`) separately:

```bash
docker compose exec db pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc > totp-auth-$(date +%F).dump
# restore:
docker compose exec -T db pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean < totp-auth-YYYY-MM-DD.dump
```

The vault in the dump is encrypted with your password-derived key, so the dump alone does
not reveal your secrets, but keep it private anyway. Also keep a plain export
(Account menu, Export) somewhere safe offline: it is the only copy that survives a forgotten
password.

## Development

```bash
npm run lint
npm run typecheck
npm test            # vitest; integration tests use DATABASE_URL_TEST and truncate it
npm run build
npm run test:e2e    # Playwright
```

Create the test database once: `docker compose exec db createdb -U totp totp_test`, then
`DATABASE_URL=$DATABASE_URL_TEST npm run db:migrate` (tests also migrate it on start).
